# Software Design

## Scope

Order creation from auction events, shipping lifecycle, buyer confirmation, dispute opening/resolution, seller escrow payout path, notification persistence, websocket, email, and push dispatch.

## Module Design

Controllers and event consumers depend on `OrderService`, `NotificationService`, `WalletClient`, and `AuthClient` interfaces. `OrderServiceImpl`, `NotificationServiceImpl`, `RestWalletClient`, and `RestAuthClient` provide the production implementations. Order command handlers, order states, dispute strategies, notification template factory, and notification channels hold specialized logic.

## SOLID Mapping

| Principle | Implementation |
|-----------|----------------|
| SRP | Controllers/routers remain thin while use-case handlers, validators, repositories, adapters, and schedulers own focused responsibilities. |
| OCP | New flows can be added through handlers/strategies/factories without modifying facade contracts. |
| LSP | Strategy, state, adapter, and client implementations are substitutable behind their interfaces/traits. |
| ISP | Interfaces are small and workflow-specific rather than one broad service abstraction. |
| DIP | Web/event layers depend on service/client interfaces, while Spring wires concrete service implementations and REST adapters. |

## Design Patterns

Facade, Command handlers, State for order lifecycle, Strategy for dispute winner handling, Template-like side-effect workflows, Factory Method for notification templates, Adapter channels for in-app/email/push.

## Compatibility Rule

Public endpoint paths, DTO shapes, routing keys, and existing constructor/service methods are kept compatible; internal refactors are implementation details.
